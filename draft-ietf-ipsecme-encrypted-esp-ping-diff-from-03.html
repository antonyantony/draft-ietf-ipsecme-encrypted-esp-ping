    intermediate network permits ESP packets by sending an unencrypted
    ESP Echo Request. Depending on whether an ESP Echo Reply is
    received, the node can choose to enable UDP encapsulation, use a

    requiring VPN or cryptographic credentials by sending unencrypted ESP
    Echo Requests. This allows enterprise support personnel to debug
    connectivity for guests independently, and enables operators to
    report path issues to transit ISPs along the routing path.

    4. Relationship with RFC 9347
   
    IP Traffic Flow Security (IP-TFS) [RFC9347] utilizes Next Header 144
    (AGGFRAG_PAYLOAD) and defines a Congestion Control payload (sub-type
    1) to measure round-trip time and packet loss within an active IP-TFS
    tunnel. The ESP Echo Protocol defined in this document also uses
    Next Header 144, defining dedicated Echo Request and Reply sub-types
    (sub-types [TBD2] and [TBD3]). The ESP Echo Protocol can be deployed
    in addition to active IP-TFS tunnels, or used independently across
    standard ESP SAs and unencrypted links.
   
    To determine which mechanism to use:
   
    * *When either can be used*: For basic link reachability checks and
    round-trip time measurement over an established, active IP-TFS
    tunnel ([RFC9347]), either mechanism can be used. When using RFC
    9347 Congestion Control payloads specifically as echo probes, they
    MUST be sent as independent ESP frames without concatenating other
    IPv4 or IPv6 data blocks.
   
    * *When to use RFC 9347 Congestion Control*: Use Congestion Control
    payloads when operating an active IP-TFS tunnel to provide real-
    time loss and delay feedback for IP-TFS rate adaptation
    algorithms.
   
    * *When to use ESP Echo*: Use the ESP Echo Protocol when verifying
    reachability, liveness, or Path MTU on standard (non-IP-TFS) ESP
    SAs; when probing specific return paths across multiple SAs; when
    sending unidirectional keepalives or maintaining NAT state without
    eliciting replies (R=0); or when probing unencrypted paths prior
    to SA negotiation (SPI 7 and 8).
    Unlike normal IP-TFS operation where Congestion Control payloads are
    multiplexed directly into the aggregation stream, ESP Echo packets
    are always transmitted as standalone ESP control frames and MUST NOT
    be aggregated or fragmented with user data.

    5.5. Unencrypted Mode (Fixed SPI 7 and 8)
   
    An IPv4 or IPv6 node that desires to determine whether the path to a
    particular destination supports ESP packets outside the context of a
    negotiated ESP SA sends an unencrypted ESP Echo Request packet to
    that destination. In this mode, packets use the standard ESP packet
    format described in Section 2 of [RFC4303] with the NULL encryption
    algorithm [RFC2410] and no integrity protection (AUTH_NONE
    [RFC7296]):
   
    * The SPI field MUST be set to 7 (ESP-ECHO-REQUEST) for requests and
    8 (ESP-ECHO-REPLY) for replies.
   
    * The Next Header field in the ESP trailer MUST be set to 144
    (AGGFRAG_PAYLOAD).
    * Under NULL encryption [RFC2410] and no integrity protection
    ([RFC4303] Section 2.7), the Initialization Vector (IV) and
    Integrity Check Value (ICV) fields are omitted (0 octets in
    length).
   
    * The ESP Sequence Number SHOULD be set to 0, and replay protection
    MUST NOT be enabled.
   
    * The ESP trailer contains 0 to 3 octets of Padding as needed to
    align the trailer to a 4-octet boundary [RFC2410], followed by a
    1-octet Pad Length and the 1-octet Next Header (144).
   
    The inner payload utilizes the same fixed format defined in
    Section 5.3. When requesting an unencrypted Echo Reply, the sender
    sets the Reply path flag (R=1) and sets the Reply path SPI field to 8
    (ESP-ECHO-REPLY). To send a one-way unencrypted probe without
    eliciting a reply, the sender sets R=0, and the Reply path SPI field
    is ignored by the receiver. Senders MAY include arbitrary data in
    the Data field up to the path MTU to verify large packet
    transmission; when R=1, the responder SHOULD copy the request data up
    to the reply path MTU.
   
    When no reply is received, a sender MUST NOT conclude that the
    network path is unable to transmit ESP packets. The absence of a
    reply can be caused by any of the following:
   
    * The remote peer does not support the ESP Echo Protocol (or local
    policy chooses not to reply).
   
    * The network path does not support ESP packets (e.g., protocol 50
    is dropped by intermediate middleboxes or firewalls).
   
    * Intermediate network nodes permit regular ESP traffic with
    operational negotiated SPIs, but drop ESP packets with reserved
    SPI values (7 or 8).
   
    Senders SHOULD still attempt to establish standard ESP Security
    Associations if no alternative paths or protocols are available.
   
    Because unencrypted ESP Echo packets operate outside the context of a
    negotiated ESP SA, receivers MUST NOT require a dynamically
    negotiated Security Association to accept and process incoming
    packets with SPI values 7 and 8 (arriving over raw ESP protocol 50 or
    UDP/TCP encapsulation). Implementations MAY process these packets
    directly or MAY utilize static SADB entries configured with NULL
    encryption ([RFC2410]) and no authentication to maintain
    administrative, policy, or rate-limiting information for unencrypted
    probing.
    5.6. Behavior under UDP and TCP Encapsulation
   
    There is no distinction between ESP Echo packets and other ESP
    packets for the purposes of processing encapsulation under [RFC3948]
    (UDP encapsulation) and [RFC8229] (TCP encapsulation).
   
    If an implementation is capable of receiving UDP or TCP encapsulated
    packets, it SHOULD accept encapsulated ESP packets with SPI values 7
    and 8 on either, without the negotiation of an SA.
   
    When TCP encapsulation is used [RFC8229], path MTU discovery is
    ineffective. Because TCP segments and reassembles stream traffic,
    packets exceeding the path MTU are segmented rather than dropped by
    network bottlenecks. Consequently, over TCP encapsulation, ESP Echo
    functions as an SA reachability and liveness check rather than an MTU
    discovery tool.
